# tf-dt-eks-secret-provider-classes

Syncs AWS Secrets Manager into Kubernetes Secrets, so the application never
holds credentials of its own.

## Why

Terraform already creates every secret the application needs — Rails keys, the
owning user password, RDS and Redis credentials — and `tf-dt-eks` already
installs the ASCP addon that can read them. What was missing was the piece in
between: the `SecretProviderClass` objects that map a Secrets Manager entry onto
a Kubernetes Secret.

That piece existed only as a Helm chart installed by hand, with its values
transcribed from `terraform output`. Every name in it carries a generated
suffix, so the transcription had to be redone after each rebuild:

```
rdsPgSecretName: prod-apple-poc-md-us1-rds-pg3c25e8d14ed119da6b4ef5e853
```

Copying generated names between tools by hand is the smell this module removes.
The names come from module outputs instead.

## Usage

```hcl
module "secret_provider_classes" {
  source  = "git::https://github.com/ad-signalio/terraform-utils.git?ref=aws/tf-hosted-modules/tf-dt-eks-secret-provider-classes/v1.0.0"
  enabled = true

  cluster_name          = module.eks.eks_cluster_name
  secret_store_role_arn = module.eks.secrets_csi_irsa_role_arn

  api_secret_name    = module.application-secrets.api_secret_name
  user_secret_name   = module.application-secrets.user_secret_name
  rds_pg_secret_name = module.rds-postgres.rds_pg_secret_name
  redis_secret_name  = module.elasticache_redis.redis_secret_name

  depends_on = [module.keda] # tf-dt-keda owns the match namespace
}
```

## What it creates

| Kubernetes Secret | From |
|---|---|
| `match-api-secrets` | `api_secret_name` — Rails keys |
| `match-owning-user-credentials` | `user_secret_name` |
| `match-postgres-credentials` | `rds_pg_secret_name` |
| `<cluster_name>-redis` | `redis_secret_name` |
| `dockerconfig` | `match-docker-secret`, account-level |
| `honeybadger-api-key` | `match-honeybadger-secret`, account-level |
| `smtp-secrets` | `smtp_secret_name`, only when set |

The last two come from fixed, account-level Secrets Manager entries that
**Terraform grants access to but never creates**. They have to exist before the
release, or the syncer produces nothing for them.

## The interlock

The application chart can generate `match-api-secrets` and
`match-owning-user-credentials` itself. With this module on, it must not:

```hcl
# terraform output -raw match_helm_values
secretKeys:
  secret: { generate: false, name: match-api-secrets }
owningUser:
  secret: { generate: false, name: match-owning-user-credentials }
```

The chart is careful — it looks the Secret up and adopts it rather than
overwriting — so a correctly ordered install works either way. The failure is a
race: install the application *first* and its `pre-install` hook writes freshly
random values, Rails boots with them, and the CSI driver then replaces
`secret_key_base` underneath a running app. Sessions break, and anything
encrypted with the old key stops decrypting.

`generate: false` removes the race rather than winning it: pods wait in
`CreateContainerConfigError` until the Secrets exist, which is loud and
self-healing.

## helm_release, not kubernetes_manifest

Deliberate. The secret names are generated by other modules and so unknown at
plan time, which `kubernetes_manifest` rejects — and it needs the cluster
reachable during plan, which is what forces staged applies elsewhere in this
repo. `helm_release` has neither restriction, so this module adds no plan-time
cluster dependency.

The chart comes from the public helm repo, so no registry credentials are
needed anywhere:

```
https://ad-signalio.github.io/helm-charts  →  secrets-configuration-aws
```

## Requirements

- The ASCP addon, which `tf-dt-eks` installs
- The `match` namespace, which `tf-dt-keda` creates
- Schedulable compute, if `wait` is left on — the syncer is a Deployment

## Troubleshooting

| Symptom | Cause |
|---|---|
| `timed out waiting for the condition` | The syncer cannot schedule. It is a Deployment, so it needs a node — apply this after compute exists, or set `wait = false` |
| Secrets never appear, release reports success | The syncer pod is what makes the CSI driver materialise them. Check it is running: nothing mounts the volumes if it is scaled to zero |
| A secret stops updating after rotation | Same cause. The driver only re-reads while a pod mounts the SecretProviderClass |
| `failed to fetch secret from all regions` | The IRSA role cannot read that entry. `tf-dt-eks`'s policy covers the cluster-prefixed names plus the two account-level ones; anything else needs adding |
| Pods in `CreateContainerConfigError` | Expected until the syncer has run. If it persists, the Secret name the application expects does not match what this module creates |
